The question

Separating a service can move a failure boundary, but it introduces delayed consistency and recovery work. This local rental-system study compares three architectures instead of assuming that separation is automatically an improvement.

The approach

Synthetic bookings exercise a coupled application, a modular application, and split invoicing. The split version records a notification in an outbox and uses a local worker with its own invoice database. Delivery can be retried; complete versioned invoice state prevents stale events from restoring cancelled invoices.

What the records show

In the saved worker-exit case, the invoice commits before the worker exits. One booking and one invoice remain, with one pending notification. After explicit retry, the notification is acknowledged and there is still exactly one invoice. The browser below displays those actual before/after snapshots.

A result that challenged the premise

The retained pricing-change study required the same two-line calculation addition across all three variants. For this particular change, architectural separation did not reduce the edit. The comparison is narrower and more useful than claiming that microservices improve maintainability.

Scope and assistance

Solo project. This is an AI-assisted command-line research prototype with shared supporting code and synthetic fixtures. The study covers correctness, local recovery, and a paused migration with exact row verification.

Limits and next investigation

There is no external message broker or networked deployment. Local failure injection does not prove production uptime, enterprise scalability, or team productivity. Further work would need independent implementations, additional change types, and real operational constraints.
